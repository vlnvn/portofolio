# 1. Product vision

Build a personal portfolio that behaves like an authored interactive technical experience rather than a template gallery.

The portfolio should make a visitor think:

> This person can build serious technical systems, but also understands interaction, presentation, and creative engineering.

The site must combine three characteristics:

- **40% Creative Developer**
- **40% Playful Experimental**
- **20% Premium Engineering**

Internal product principle:

> **Creative outside, structured inside.**

The visual shell may be bold, cinematic, asymmetric, interactive, and experimental. The information architecture underneath must remain easy to understand for recruiters, engineers, lecturers, collaborators, and conservative HR reviewers.

---

# 2. Product problem

The rejected V1 direction optimized too heavily for restraint, evidence density, and anti-slop rules.

That produced:

- muted green/teal visual identity;
- low visual contrast between projects;
- basic two-column/register composition;
- limited art direction;
- minimal motion;
- generic developer-portfolio impression;
- insufficient expression of creative-development ability.

V2 must keep the factual discipline and evidence clarity of V1 while replacing its visual language entirely.

V2 is **not** a visual polish pass over V1. It is a new visual system.

# 8. Signature visual actor — The Signal Form

## 8.1 Purpose

The Signal Form is the primary visual signature of the portfolio.

It represents technical systems, connections, transformation, and experimentation without pretending to visualize actual project data.

## 8.2 Visual ingredients

Possible construction language:

- modular geometry;
- nodes;
- ribbons or paths;
- planes;
- linked structures;
- translucent materials;
- semi-metallic materials;
- wireframe detail;
- controlled light emission;
- soft volumetric/bloom response.

## 8.3 Forbidden forms

Do not default to:

- generic floating sphere;
- torus knot used only because it is easy;
- chrome blob;
- purple particle cloud;
- AI neural-network globe;
- random constellation;
- holographic ball;
- decorative geometry unrelated to the project transitions.

## 8.4 One object, multiple states

The Signal Form must clearly remain one evolving object.

### Hero state

Abstract, unresolved, alive.

### 01 — KAIROS

More ordered, ranked, directional, or prioritized.

Must not look like actual KAIROS evaluation data.

### 02 — Ayam Kalintang

More modular, tactile, workflow-oriented.

Must not mimic the restaurant UI.

### 03 — The Colors of MIPA

More connected, distributed, social, or spatial.

Must not imply literal contributor counts through node count.

### 04 — Aether3D

Most explicit mesh / geometry / wireframe state.

### 05 — N.A.R.A.

Layered connected planes or structured interface/system state.

## 8.5 3D presence

Preferred scope:

- hero;
- project chapter transitions;
- selected key moments.

Do not make the 3D canvas dominate the entire page continuously.

The visitor should periodically return attention to real work.

# 11. Theme system

## 11.1 Light mode

Desired direction:

- soft cold off-white;
- not pure `#FFFFFF` everywhere;
- near-black navy text;
- dusty/slate blue identity;
- controlled cobalt/electric/ice-blue energy;
- subtle blue-grey surfaces.

The overall feel should be clean rather than sterile.

## 11.2 Dark mode

Desired direction:

- near-black navy / deep midnight blue;
- not pure black;
- independently tuned surfaces;
- more dramatic cinematic depth;
- brighter controlled blue energy;
- no neon gamer/cyberpunk look.

Dark mode may be more dramatic than light mode.

It does not need to be a simple color inversion.

## 11.3 Exact palette

Do **not** freeze final hex values before the V2 visual DNA and hero are approved.

The Figma visual exploration determines the final token values.

## 11.4 Project secondary accents

Allowed.

Global blue identity remains dominant.

Small secondary accent may distinguish each project through:

- artifact surround;
- small typographic moment;
- 3D material/light state;
- transition detail.

Do not create five independent brand palettes.

---

# 12. Gradient, light, glow, and material policy

Gradients are allowed.

Glow/bloom is allowed at low-to-medium intensity.

Prefer:

- directional slate → blue transitions;
- blue/cobalt/ice material response;
- lighting-driven gradients;
- controlled atmospheric depth;
- physically plausible material changes.

Reject:

- purple-cyan AI blob;
- pink-purple mesh;
- rainbow holographic treatment;
- repeated radial blobs behind content;
- aurora background on every section.

Glow should reinforce light/material.

Glow is not a substitute for composition.

# 13. Typography

## 13.1 Direction

Use:

- **large medium/light display typography**
- **clean readable sans body**

Two font families are allowed.

## 13.2 Desired character

Display:

- modern;
- slightly expressive;
- large;
- controlled;
- not ultra-bold.

Body:

- highly readable;
- technical without feeling corporate;
- excellent at 16–18px.

## 13.3 Forbidden defaulting

Do not choose a font only because it is a common developer default.

Do not automatically use:

- Inter;
- Geist;
- Space Grotesk;
- IBM Plex Sans.

They remain permissible only if actual visual comparison proves they are the best choice.

## 13.4 Monospace

Allowed sparingly.

Use only for meaningful technical information such as:

- compact technical metadata;
- real code/evidence label;
- chapter/technical annotation where justified.

Do not use monospace as developer cosplay.

# 22. Motion system

## 22.1 Intent

Motion explains:

- progression;
- state;
- project change;
- spatial relationship;
- interaction response.

Motion does not exist merely to “make it premium.”

## 22.2 Allowed motion

- Signal Form morph;
- object repositioning;
- chapter transition;
- nav transformation;
- progress-line movement;
- portrait/3D parallax;
- subtle media tilt;
- clip/mask reveal;
- artifact reframing;
- type transition;
- case-study visual expansion concept.

## 22.3 Forbidden motion

- identical fade-up on every element;
- constant parallax background;
- bouncing CTAs;
- excessive spring motion;
- looping decorative animations everywhere;
- hover transforms on every card;
- page-wide cursor trails;
- scroll-jacking.

## 22.4 Critical content rule

Critical content must be present and accessible without waiting for an animation.

Never require animation completion to read:

- project title;
- role;
- key evidence;
- source link.

Mobile is a designed translation, not a shrunken desktop.

# 26. Performance requirements

Creative expression is allowed to cost more than the rejected V1, but it remains bounded.

## Intended budget

Target initial experience:

**approximately 2–3 MB compressed maximum**, only if the visual experience earns the weight.

This is a target, not permission to fill the budget.

## 3D requirements

Future production should consider:

- progressive asset loading;
- low-resolution/poster fallback;
- reusable geometry/materials;
- compressed models/textures;
- adaptive DPR;
- lower-quality effects on weak devices;
- demand/idle rendering where appropriate;
- LOD when useful;
- no permanent heavy render loop when the scene is static.

## Failure behavior

If WebGL is unsupported or unstable:

- content still renders;
- navigation works;
- project evidence remains accessible;
- static Signal Form art may replace the scene.

The portfolio must never fail because 3D failed.

# 27. Accessibility requirements

Target: WCAG 2.2 AA for production content and interactions.

Required:

- semantic landmarks;
- one H1 per route;
- logical headings;
- keyboard navigation;
- visible focus;
- accessible theme control;
- meaningful link labels;
- sufficient contrast;
- touch targets;
- no horizontal overflow at 320px;
- 200% zoom resilience;
- alt text for evidence-bearing images;
- video fallback/captions where relevant.

## Reduced motion

When `prefers-reduced-motion: reduce`:

- disable non-essential 3D morph;
- remove large panning/scaling transitions;
- remove parallax;
- remove tilt;
- use static or low-motion Signal Form;
- preserve chapter states without animated travel;
- preserve all content and navigation.

Reduced motion is an alternate experience, not a broken version.

# 42. Change-control protocol

When a design/engineering decision is not covered here:

### Step 1 — classify

`LOCAL`  
Does not change the grand design.

`SYSTEM`  
Changes repeated visual/interaction behavior.

`GRAND DESIGN`  
Changes frozen decisions, hierarchy, identity, or product concept.

### Step 2 — action

**LOCAL:** agent may decide and document.

**SYSTEM:** agent may prototype but must compare alternatives before locking.

**GRAND DESIGN:** stop and request user approval.

Examples of GRAND DESIGN changes:

- changing blue identity to another dominant hue;
- removing portrait;
- removing Signal Form;
- changing all projects back to a register/grid;
- removing 3D;
- replacing chapter navigation with normal static nav;
- changing project hierarchy;
- making the site minimalist again;
- introducing a SaaS-style hero;
- adding a new global visual motif.
